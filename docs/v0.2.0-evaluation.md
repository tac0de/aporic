# Aporic 0.2.0 evaluation checkpoint

This checkpoint records implementation evidence used for the `0.2.0` release. It is not a production-security claim.

## Governance behavior

- The same pure evaluator drives SessionStart status, read-only `explain`, and PreToolUse admission.
- A bounded grant is exact to plan, scope, session, tool, and JSON tool input.
- Concurrent one-shot admission allows at most one caller and records one consumption.
- Holds precede authority; reused tool-use IDs and mismatched inputs do not consume a grant.
- `doctor` and `explain` do not change the store revision.
- v1 migration preserves source bytes and refuses an existing destination.

These claims are covered by the Rust regression suite, including `tests/v020.rs`.

## Context-size comparison

For an empty store, one protected `apply_patch` tool, required plan authority, and the same SessionStart input:

| Version | Wrapped context bytes |
| --- | ---: |
| 0.1.0 (`69d17e7`) | 892 |
| 0.2.0 working tree | 1,000 |

The v0.2 projection is 108 bytes (12.11%) larger in this minimum case because it declares multi-tool and grant policy plus explicit protected/omitted tool counts. An omission receipt and omitted-status aggregate are emitted only when details are actually omitted. Action-specific `explain` output is requested on demand rather than injected at every session start.

Measurement used serialized `additionalContext` UTF-8 bytes. It did not use a model tokenizer, so this is not evidence of token or cost reduction.

## Residual boundaries

- Grant consumption attests preflight admission, not tool success or filesystem effect.
- Exact grant input is stored and can expose secrets if an issuer includes them.
- FNV identities are informational only; exact JSON equality is the authorization check.
- The packaged default protects `apply_patch`; additional exact tool names require policy changes and host-level validation.
- macOS arm64 is the only packaged target exercised locally.
