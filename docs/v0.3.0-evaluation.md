# Aporic 0.3.0 evaluation checkpoint

This checkpoint records implementation evidence for the `0.3.0` release. It is not a production-security claim.

## Global adapter behavior

- One static Codex plugin package contains no project path, scope, or policy.
- A project opts in with `.aporic/config.json`; the nearest binding above the hook `cwd` wins.
- Unbound workspaces produce no PreToolUse decision and only a continuation response at SessionStart.
- Invalid bindings and policies fail closed for PreToolUse instead of relying on hook-process failure behavior.
- Project stores are required to resolve outside repositories and are isolated by a lossless versioned encoding of the canonical absolute workspace path under `${APORIC_DATA_HOME:-$HOME/.local/share/aporic}`.
- `project-init` refuses to replace binding, policy, or store files.
- v1 cutover requires stopped source writers and a scope check; invalid migration input is rejected before the project binding is published.

These claims are covered by unit and CLI regression tests, including packaged-binary end-to-end execution.

## Verification environment

- Full test suite: 84 tests passed with the local stable Rust toolchain.
- MSRV suite: the same 84 tests passed with Rust `1.89.0`.
- `cargo fmt --check` passed.
- `cargo clippy --all-targets --locked -- -D warnings` passed.
- A fresh macOS arm64 plugin package passed the Codex plugin validator.
- The packaged binary initialized a bound project, resolved a nested working directory, projected the configured scope, and emitted no decision for an unrelated workspace.

## Residual boundaries

- Moving or renaming a project changes its resolved store path; migration is explicit.
- A missing binding intentionally disables Aporic for that project. Same-user removal or mutation remains outside the security boundary.
- The packaged host remains macOS arm64 only.
- Hook trust and plugin replacement remain Codex host state and require a new task after installation.
